# Cloudflare Pages Functions setup (local scaffold)

The API lives in `[[path]].js` as a Pages Functions catch-all route. It is not active on the simple local static preview (`127.0.0.1:4173`); that preview only exercises browser-side demo behavior. Cloudflare Pages Functions require the Pages runtime and configured bindings. The repository has not been deployed or connected to live services.

The root `wrangler.jsonc` is prepared for **local-only Pages development**. It creates local simulated D1 and R2 bindings; the database ID and R2 bucket name are placeholders and must be replaced before any remote deployment. Do not deploy this configuration as-is. Install project dependencies with `npm install`, run `npm run dev` to serve the files and Functions (usually `http://localhost:8788`). The dev script explicitly loads `.dev.vars` because this project needs those credentials in the Pages runtime. Initialize the local D1 database once with `npm run db:local:init`. A fresh database uses the current `schema.sql` only. Existing databases should apply only missing migrations in order through `0009_commission_open_state.sql`, after a backup. The 0005 migration preserves old BRL payment and publication amounts; 0008 preserves existing payment rows while adding the reviewed-transfer provider. Before `0004`, resolve any duplicate active payment attempts. Never apply remote migrations without confirming the database state and backup.

Copy `.dev.vars.example` to `.dev.vars` for local secrets; `.dev.vars` is ignored by Git. Google, Discord and Twitter sign-in use server-side OAuth flows and their local provider credentials are configured. Register the exact callback on the hostname used in the browser (`127.0.0.1` and `localhost` are different origins): `/api/auth/google/callback`, `/api/auth/discord/callback`, and `/api/auth/x/callback`. The Google client ID may remain in `profile-config.js` for public site configuration; all client secrets must stay server-side. The user-facing provider name is Twitter while its API/configuration retain X naming. Discord needs `identify email`; Twitter uses OAuth 2.0 Authorization Code + PKCE S256 and `users.read users.email`. The providers must return a verified email because orders require a customer email. Each provider account gets its own identity; accounts are not joined automatically by matching emails. Keep `PUBLIC_SITE_URL` unset while local-only; payment providers require externally reachable return/webhook URLs, so checkout remains disabled. The static preview at `127.0.0.1:4173` does not run Functions; use Wrangler to exercise login, APIs, email, and uploads. Local D1/R2 simulations stay on this machine and are not shared with customers or Cloudflare.

For a future remote Pages environment, bind D1 as `DB` and an R2 bucket as `MEDIA_BUCKET`, then configure encrypted runtime secrets/variables:

- `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`: credentials from a Google OAuth client of type Web application. Register the exact HTTPS callback `/api/auth/google/callback` on the public origin before enabling Google login there.
- Optional Discord order DMs: `DISCORD_BOT_TOKEN` and `DISCORD_NOTIFY_USER_ID`. This is a bot token from the Bot page, separate from `DISCORD_CLIENT_SECRET`; the recipient ID is your Discord user ID. Add the bot to a server you share with that user, then start a DM with it. The integration opens the DM and sends only new-order alerts. Missing values disable this notification without affecting order creation or email.
- `DISCORD_CLIENT_ID` and `DISCORD_CLIENT_SECRET`: Discord OAuth2 app credentials.
- `X_CLIENT_ID` and `X_CLIENT_SECRET`: X OAuth 2.0 confidential Web App credentials.
- `SESSION_SECRET`: randomly generated secret, at least 32 characters.
- `RESEND_API_KEY`, `MAIL_FROM`, `MAIL_REPLY_TO`, and `ADMIN_EMAIL` (`nnytro.online@gmail.com`) for transactional email. The Gmail address is the reply-to/admin recipient; the sender must use your exact verified domain (the local example uses `pedidos@nnytro.online`, only if that domain is verified in Resend). DNS verification is done by adding Resend's records at the domain DNS host, not by verifying a Gmail inbox. Without these values, mail is disabled; state updates still save, but no email is sent.
- `PUBLIC_SITE_URL`: the exact public site origin with HTTPS (for example `https://nnytro.online`). Checkout creation refuses local, insecure, or missing origins.
- `MEDIA_BUCKET`: Cloudflare R2 binding used for admin-only commission media uploads. Admin publication upload accepts JPG, PNG, WEBP, GIF, MP4 and WEBM, up to 24 MiB per file. Files receive random server-generated object keys; the `/api/media/gallery/...` route serves only objects tagged as commission gallery media, with `private, no-store` caching and `nosniff`. Anonymous visitors can fetch an object only after its exact URL is referenced by a published gallery case; a verified admin session can preview unpublished uploads. No public R2 bucket URL is required. Local static preview does not provide this route; Cloudflare Pages Functions plus the R2 binding are required.
- `MERCADOPAGO_ACCESS_TOKEN` and `MERCADOPAGO_WEBHOOK_SECRET`: credentials for the seller application and signed webhook notifications. Keep unset until the seller's account country/currency and the displayed USD-to-local-currency conversion policy are chosen.
- `PAYPAL_ENV` (`sandbox` or `live`), `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, and `PAYPAL_WEBHOOK_ID`: credentials and webhook ID from the same PayPal REST app/environment. Configure the webhook URL as `https://<site-origin>/api/payments/webhook?provider=paypal` and subscribe to `PAYMENT.CAPTURE.COMPLETED` and `PAYMENT.CAPTURE.REFUNDED`.

The API does not read an `ALLOWED_ORIGINS` setting. State-changing browser requests must provide an exact same-origin `Origin` header; provider webhook requests are excluded from this browser-origin check and rely on their provider signature verification. Never commit secrets or place them in browser code. Admin access is checked against the verified Google email `nnytro.online@gmail.com`; Discord/X users cannot become administrators by matching an email. D1 holds users, orders, event history, messages, payment records, gallery cases, and reviews. Customer endpoints scope reads and writes to the provider-namespaced authenticated subject. `/api/profile` lets a user edit their chosen display name and HTTPS avatar URL. `/api/admin/profile` returns admin-only order counts and is restricted to the verified admin session.

Implemented in the repository: customer profile and order views, Google, Discord and Twitter sign-in UI/API flows, admin order/profile controls, private per-order support tickets, completed-commission gallery and review UI. These frontends call `/api/*`; the static local preview does not provide a backend. The local provider-status endpoint reports all three providers enabled. Each callback still needs to match the exact browser hostname and provider-app configuration. Social sign-in creates a provider-specific customer identity so it can own orders and messages; admin endpoints remain restricted to the verified Google account `nnytro.online@gmail.com`. The support-ticket panel refreshes by polling every 2 seconds while open and notifies the other participant by email; it does not use a persistent WebSocket connection.

When configured, new orders email the administrator and customer; state changes create separate customer/admin notices; private chat messages notify the other participant without exposing message contents in the email; publication notifies the customer to review. Messages use responsive HTML and text fallbacks. Delivery is best-effort; Resend failures do not undo saved orders or messages. The local `onboarding@resend.dev` sender is a test sender. A successful API response means Resend accepted the message, not that the recipient's inbox received it. Check the message status in Resend and spam/promotions; use a sender on a verified domain for normal use.

## Payment and publication flow

New admin quotes are in USD and use `full` or `deposit_50`. Intended transitions are `awaiting_full_payment → paid → in_progress → completed_paid`, and `awaiting_advance → advance_paid → in_progress → awaiting_balance → paid → completed_paid`. After the work is completed and fully paid, the verified administrator can publish the commission. The publication endpoint checks verified paid ledger rows covering the complete USD quote, final media, and matching final USD price; the public display name is optional. Published gallery output contains the chosen display name only when provided, case content and review, never order IDs, Google subject, customer email or private contact details. The legacy database consent flags remain for compatibility and are not required to publish.

Reviews require the customer's own published, fully paid order and are limited to one per order. Rating is 0–5, with optional text.

## Payment endpoints and launch requirements

PayPal checkout in USD requires a configured sandbox app and public HTTPS callback. The user now has local manual transfer aliases for USD and ARS. Manual transfer is supported as a report-and-review flow: the buyer reports the transfer; it stays pending until the verified Google administrator confirms the deposit after checking the receiving account. ARS keeps the order quote in USD and stores the agreed local amount and implied exchange rate in the private receipt; NNytro must agree to that amount in the order support ticket before the buyer sends it. Confirmation updates the same verified USD ledger used for deposits, balances, and publication eligibility. Mercado Pago/Pix remain blocked pending provider sandbox credentials, a Brazilian receiving account for Pix, explicit USD-to-BRL conversion policy, and currency-aware webhook reconciliation. Authenticated `GET /api/orders/:id/payments` returns payment/receipt summaries only to that order's customer or an administrator; the profile's “Ver recibos” control uses this private endpoint. Receipt details are not exposed in the public commissions gallery.

The legacy Mercado Pago webhook handler is retained for compatibility but does not verify BRL payments against new USD quotes. `POST /api/payments/webhook?provider=paypal` asks PayPal's verify-webhook-signature API to validate the transmission, then fetches the canonical capture/order. Both handlers match the stored internal payment identifier, approved currency and amount, and provider status before recording a receipt or advancing the order. Retries update the same payment attempt; signed webhook replays don't grant duplicate order transitions. Unknown/mismatched payments are never applied to an order. Do not activate Mercado Pago webhooks for new USD orders.

For existing BRL databases, back them up and apply only missing migrations in order through `0009_commission_open_state.sql`; a fresh database uses `schema.sql` alone. The 0005–0008 migrations leave previous BRL quotes and publication amounts in historical fields and do not convert them. For PayPal sandbox, add credentials from one sandbox REST app, create the sandbox webhook at `/api/payments/webhook?provider=paypal`, and set the matching `PAYPAL_WEBHOOK_ID`; webhooks need a public HTTPS URL. For Mercado Pago, create a test seller application and configure its access token plus the webhook signing secret. Pix uses Mercado Pago's Brazil account/payment flow rather than a separate Pix integration; the seller needs Pix enabled. Before accepting either method, choose how an USD quote is converted (source, timestamp/expiry, rounding and who absorbs fees) and store that charged amount/currency/rate in each payment. This project remains local and has not been deployed or connected to payment credentials. Do not configure live secrets or accept real payments before webhook URLs are reachable over HTTPS and all payment/refund behavior has been reviewed in sandbox.

Remaining work includes adding Discord/Twitter OAuth IDs and secrets and registering exact callbacks; configuring PayPal and Mercado Pago sandbox credentials plus public HTTPS webhook URLs; deciding the visible conversion from the USD quote to the currency collected by Mercado Pago/Pix; and then implementing and sandbox-testing that converted-currency ledger path before enabling either method. D1, the `MEDIA_BUCKET` R2 binding, responsive visual QA and verified production mail sender are also launch requirements. Never commit secrets or use live seller tokens in a repository or browser.
